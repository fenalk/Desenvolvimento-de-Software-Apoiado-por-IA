## Contexto

Pedi para o Claude Code resolver o problema apresentado na descrição da PR, propondo um fix próprio pra `docling/utils/chandra_utils.py`, e só depois comparar com o diff real. O bug: o parser de HTML do Chandra só tratava blocos com `data-label="Table"` como tabela; blocos `data-label="Form"` que continham uma `<table>` HTML dentro caíam no fallback genérico e viravam texto solto, perdendo toda a estrutura tabular.

## O diff real

```python
if label_str == "Table":
    table_data = _parse_table_html(inner_html)
    doc.add_table(data=table_data, prov=prov)
elif label_str == "Form" and "<table" in inner_html.lower():
    table_data = _parse_table_html(inner_html)
    doc.add_table(data=table_data, prov=prov)
elif label_str == "List-Group":
    ...
```

Mais teste em `tests/test_chandra_vlm.py`:

```python
def test_chandra_form_table_parsing():
    """Test a saved Chandra prediction containing tables labeled as Form."""
    path = Path("./tests/data/html_chandra/sources/chandra_form_table.html")
    content = path.read_text()

    doc = parse_chandra_html(
        content=content,
        original_page_size=Size(width=612, height=792),
```

## Minha comparação

A lógica central bateu certo: o Claude identificou a mesma condição, checar `label == "Form"` **e** presença de `<table>` no `inner_html`, roteando pro mesmo caminho de `_parse_table_html` + `doc.add_table`. Isso é o que importa, é a ideia central do fix.

As diferenças foram todas de estilo, não de abordagem:

- **Estrutura da condição:** o Claude ser mais "DRY" e uniu tudo numa condição só (`if "Table" or (...)`), sem duplicar as duas linhas de `_parse_table_html`/`add_table`. O dev autor da PR preferiu um `elif` separado, mesmo duplicando essas duas linhas. Pra um fix desse tamanho, acho o `elif` separado mais fácil de ler no diff e de reverter isoladamente se precisar, faz sentido o approach do dev aqui.
  
- **Detecção de `<table>`:** a IA usou regex pré-compilado (`re.compile(r"<table\b", re.IGNORECASE)`), o dev usou `"<table" in inner_html.lower()`. Regex é mais "correto" (evita casar `<table-of-contents>`, por exemplo), mas na prática o output do Chandra não gera esse tipo de tag, então a simplicidade do dev também é uma escolha válida — menos código pra manter.
  
- **`original_page_size` no teste:** a IA chutou `Size(width=1000, height=1000)`. O dev usou `Size(width=612, height=792)`, que é o tamanho real de uma página US Letter em pontos, mais realista e provavelmente o padrão usado nos outros testes do arquivo.
  
- **Onde colocou o teste:** o Claude sugeriu um arquivo novo (`tests/test_chandra_utils.py`). O dev colocou no arquivo já existente `tests/test_chandra_vlm.py`, junto dos outros testes de Chandra (`test_chandra_table_parsing`, `test_chandra_list_group_prediction_sample`). Faz mais sentido manter no arquivo existente pra não fragmentar os testes de VLM.
  
- **Rigor do assert:** a IA validou `num_rows > 0` / `num_cols > 0` em cada tabela e ainda conferia o texto do bloco `Text` no meio. O dev foi direto: só `assert len(doc.tables) == 4`. Pra um fix pontual e regressivo, o assert mínimo do dev é suficiente — não precisa validar conteúdo que já é responsabilidade de `_parse_table_html` (testado em outro lugar).

**Conclusão:** Claude acertou o fix em si, mas foi mais verbosa/defensiva do que o necessário em teste e escolheu uma abordagem ligeiramente mais "elegante" na condição que, na prática, o time real não achou necessária. Pra PRs de fix pequeno e cirúrgico como esse, a simplicidade do dev (duplicar duas linhas, assert mínimo) parece ser o padrão esperado no projeto.
